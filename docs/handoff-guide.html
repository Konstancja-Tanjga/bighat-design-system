Adopting bighat

Three rules stand between installing this library and shipping a screen with it. Here is what they are, what enforces each one, and what the build cannot see for you.

Why this exists

Four things a passing build cannot see

Every rule in this system exists because correct-looking, type-checking, lint-passing code can still break it. That is the only kind of rule worth writing down — the rest are already the compiler's job.

2

token layers, one API

Primitives say what a value is. Semantics say what it means. Product code may only touch the second — but importing the first compiles perfectly.

58

contrast assertions in CI

Every foreground/background pair the system promises to keep legible, checked in both themes against the WCAG rule that actually applies to it.

39

components, and a list of what each is not for

Reaching for the adjacent component is invisible to every tool. components.json carries the negative case for exactly that reason.

0

typography tokens

The system exports none. Type sizes are the one place you will be pushed off-system today — named here rather than discovered by you in week three.

The rules

Three questions, kept apart

A screen can use only approved tokens and still be unusable. It can be usable and still fall apart the moment a request returns nothing. Different failures, so they get different answers — never one summary that hides two of them.

Is it token-legal?

Colour from the semantic layer only — var(--bh-text-muted), never #59636f and never color.neutral[600]. Every gap, padding and margin from the scale. padding: 13px is wrong including when it looks better.

Enforced by npm run tokens:check, the lint rule, and review

Is it usable?

A required label on every field. Colour never the only carrier of meaning. No outline: none, ever. Named landmarks on every panel and rail. A pointer-free equivalent for every drag.

Enforced by required props, the contrast gate, and review

Is it state-complete?

Empty, loading and error are StateBlock — not a bespoke div, not null, not red text. And "empty" is two screens: nothing yet wants onboarding, nothing matching wants a way out of the filter.

Enforced by nothing automatic — this one is on you

Where the checks fire

One direction, and a way back

Day one

Install, mount, theme

The package is not on a registry — versioning is automated here, publication is not, and a dead npm install line at the top of a README helps nobody. Install from the repository:

npm install github:Konstancja-Tanjga/bighat-design-system

Mount once per application. The bh-root class is where the token values land; ToastProvider is what makes toast() reachable from anywhere below it.

import '@bighat/ui/styles.css';
import { ToastProvider, Button } from '@bighat/ui';

export function App() {
  return (
    <div className="bh-root">
      <ToastProvider>
        <Button tone="critical">Delete workspace</Button>
      </ToastProvider>
    </div>
  );
}

Dark theme is one attribute: document.documentElement.setAttribute('data-theme', 'dark'). Users who never touch a toggle get prefers-color-scheme without you writing anything.

Prototype to handoff

Say what you want

You never need to remember a rule number or a script name. A prototype built on these components is handed over by describing the outcome you want checked — agent/SKILL.md holds the rules the types cannot express, components.json holds the inventory including what each component is not for, and the agent routes from there.

Review the UX quality of this prototype.Runs the automated sweep — npm run verify: lint, token sync, 134 tests including the 58 contrast assertions — then walks the checks a script cannot make, and returns one verdict per rule rather than a summary.
Is this handoff-safe?All three gates plus the closeout: no primitives and no off-scale values left in product code, four states present on every surface that can be empty, every local component named as local. Reported as separate verdicts, because they fail for different reasons.
The spacing on this screen looks off.Answered in scale steps — tight, snug, normal, loose — and in the relations between them, never in pixels. A pixel answer is a value that will drift the moment the scale moves.
bighat cannot do what I need here.Checks whether that is true against the inventory and the six named gaps first, then builds it locally in semantic tokens and says out loud that it is local — so the next screen finds a documented gap instead of a lookalike.
Should this become a bighat component?Weighs it honestly, including the case against — most things should stay in the product — and drafts a proposal for you to file. The second occurrence in a different screen is the evidence; the first is a local component.

Two of those answers end at your desk on purpose. Filing a proposal, and deciding that a prototype is done, are commitments on somebody’s behalf, and they should carry the name of the person who stands behind them.

Whether that changes anything is a testable claim, so it was tested

agent/EVIDENCE.md is the comparison: same model, same prompt, skill file present or absent, both outputs committed verbatim. The result contradicted the hypothesis. None of the four predicted rule failures happened in either run — because the rules are also in the component source, in the README, and in required props. What the skill file changed was architectural: without it, a table with a toolbar and no landmarks; with it, a full AppShell with named regions and a skip link. Both runs then left raw font sizes inline, because the system exports no typography tokens.

Reading a result

Three verdicts, and one of them is not a verdict

npm run verify runs lint, formatting, the token sync check, 134 tests and both builds, in that order, and stops at the first failure.

Pass

Measured, and it holds. The contrast gate knows a focus ring is non-text, so it asks 3:1 rather than pushing the palette to mud for an absurd 4.5:1.

Fail

Measured, and it breaches. You get the pair, the theme, the required ratio and the observed one — enough to fix it without a follow-up question. A palette tweak that looks better but drops text.muted to 4.3:1 lands here.

Not enforceable

No gate can tell you that ariaLabel="Panel" names nothing, that your empty state answers the wrong one of the two empty cases, or that a board card can only be moved by dragging. These are in agent/SKILL.md precisely because CI cannot reach them.

Not enforceable is not a soft pass

It blocks a review exactly as a failure does. The difference is what fixes it: a failure needs a change to the code, an unenforceable rule needs somebody to look. A rule nobody checked is never reported as holding — that is the whole reason these results are worth reading.

When the system can't

What to do when nothing maps

This is the part that goes wrong quietly, because the wrong version compiles. Follow it in order.

  1. Use the component, and prefer the higher-level one

    Table takes a state prop typed as StateBlockProps and renders it across every column. AppShell owns the four landmark regions. Composing that yourself from smaller parts is not neutral — it is a second implementation to keep correct.

  2. If nothing maps, stop

    Do not approximate. A hand-built control that looks like the system is worse than a documented gap, because it ships as though it were supported. Six components are named as missing on purpose — Textarea, Chip, FileDropzone, Pagination, Tree, Stepper — so nobody quietly widens something adjacent instead.

  3. Build it locally, in semantic tokens, and say that it is local

    Product code is the right place for a one-off. Say plainly in the code and in the review that it is a local component. What is not acceptable is adding a prop to a system component to cover a single screen: Button will not grow variant="link" — that is an anchor.

  4. Propose the role or the component, and name the cost

    A new colour needs a role before it can be used, which means a hex on its own is not a handover. That friction is the feature. A proposal that survives says what it is for, what it is not for, and what breaks if it is refused.

  5. Second occurrence is the evidence, not the first

    One screen needing something is a local component. The same gap in two products is a case the system can act on. Filing that stays a human step: asking a design system to grow is a maintenance commitment, and it should carry the name of the person who stands behind it.

Before you touch it

Five things worth knowing first

14px base Not 16. The type scale runs 11 / 13 / 14 / 16 / 20 / 26, and there are no typography tokens exported yet — so a size you set today is a size you will migrate later. Keep them in one place.
4px scale Spacing is --bh-gap-tight | snug | normal | loose (4 / 8 / 12 / 16) and --bh-padding-inline | block | section (12 / 8 / 24). Names, not numbers, so the values can move without a find-and-replace.
native first Select, Dialog, DatePicker, Slider and ScrollArea are the platform's own, wrapped. Focus trapping, autofill, page inertness and mobile behaviour are not worth reimplementing badly. Combobox is the single refusal of that bargain, and it pays the full ARIA bill.
templates are copies The two page templates live in Storybook and are deliberately not exported. A template you install becomes a dependency, and then a team is blocked on the design system to change its own layout. Copy one in, and keep all four states — deleting the error story deletes the part that was hard.
tokens.css is generated src/styles/tokens.css comes from src/tokens/*.ts via npm run tokens. Edit the TypeScript, never the CSS. CI fails if the committed CSS has drifted from its source.

Upgrading

If it behaves differently for you

Run npm run verify first. When one machine disagrees with another it is almost always drift rather than the library — a hand-edited tokens.css, a stale dist, or a branch that has not caught up with main.

If you are arriving from 2.x, one thing was removed rather than deprecated forever. Button variant="danger" was doing two jobs — four values described visual weight, one described consequence — so 3.0 split it into variant for weight and tone for consequence. Through the whole of 2.x the old value kept rendering byte-identically, asserted by a test, while warning once in development; that is what let a team take the major on a Tuesday and do the rename whenever they got to it. 3.0 closed the window. A deprecation that never ends is not a deprecation, it is a second API you have quietly agreed to maintain forever.

  • If verify comes back clean and the behaviour still differs, that is worth reporting: it means a check is missing, and the fix is to add one rather than to remember the workaround.
